# 环境、基线和受约束的实验

这份手册决定实验怎样执行和判读。不能把写作技能中的叙事、措辞或优势展示规则用于选择指标、基线、样本或保留哪些结果。

## 固定评测条件

环境文件记录 Python、框架、依赖锁定版本、CUDA/驱动、硬件及安装命令。评测脚本应该是实际使用的代码，不是只写了一行说明的占位文件。切分清单记录数据版本/校验和、样本或时间范围、预处理规则及划分生成命令。

严格防止训练、验证、测试之间的信息泄漏。预处理和归一化只拟合训练集。重复个体、视频、患者、文档或时间窗口按真实独立单位划分。时间序列中特别核对目标时间、窗口重叠、预测时不可得的协变量与反归一化。

主指标、方向、模型、数据集、种子、调参规则与停止规则在 protocol.json 指定。先选研究问题需要的比较条件，再决定控制参数量、训练计算量、数据、推理延迟或内存。等参数不自动等计算，等计算也不自动覆盖部署限制。对无法同时匹配的条件如实说明，必要时给出多组控制。

冻结后的协议、假设、预算、评测、环境和切分均有版本指纹。`freeze --reason` 建立新版本会回到 pilot，旧运行继续保留。若已看过测试结果，版本变更本身不能恢复统计独立性，另行规划独立确认材料。

## 先复现强基线

基线应包括合理的简单方法、直接相关强方法和必要的容量/算力控制。记录官方代码版本、默认配置、调参范围、验证集选择规则和实际搜索预算。基线与候选使用透明、合理的调参资源；不能故意少调基线来制造收益。

先核对能否复现官方或可信公开设置的结果。出现差异要找原因：数据版本、预处理、训练步数、评测口径、硬件、随机性或代码错误。复现成本过高时明确采用可负担的设置，缩小贡献范围，不能冒称复现了完整 SOTA。

## 短实验分两层

- **smoke**：一次前向/反向、有限值、张量维度、设备、checkpoint 保存与恢复。所谓“五秒”只是快速反馈的比喻；编译、缓存和硬件使固定墙钟时间不可比。
- **pilot**：小数据过拟合、手算/独立实现核对指标、关键分支覆盖、数据泄漏审计、基线复现检查、成本估算和调参。按相同步数或样本数比较调试行为。

在 pilot.json 的六项必要检查中附实际证据。新增 evaluator_sensitivity 要证明当前评测能区分预设对照，见 [评测有效性验收](evaluator-validation.md)，不能用 na 跳过。非神经方法可将 gradient 或 tiny_overfit 标为 na，给出原因和等价验证证据。不能把“没报错”当作通过正确性检查，也不能从极短训练排名推出架构优劣。

pilot 审查验收的是环境和基线，绑定 pilot.json 及基线的 smoke/pilot；新增候选运行不使基线验收失效。修改评测、数据、基线代码或配置必须修订协议并重新验收。每个 baseline/dataset 组合都要有 pilot 证据。候选也须在相应数据上完成 pilot 才能交给执行器做正式实验。

首次可以冻结只有 baselines、candidates=[] 的协议，不必为了填表先造模块。此时 hypothesis.json 写待核实的基线失效及诊断预测，明确标为初始判断。通过验收再 propose；实现候选、确定配置后 freeze --reason 建立下一版本，并做短回归检查。已有长运行保留供诊断，不能改标签进入新版本的正式汇总。

pilot 审查通过后才运行完整网格。审查只确认已检查范围中的已知重要问题被处理，不证明不存在其他错误。

## 正式运行与自动搜索

Agent 可以在已固定的环境内探索结构。自动搜索仍要限制候选数、每次和总成本，并使用 validation 选择。探索全部登记为 pilot；选定方案与超参后再冻结用于确认的协议及独立评测计划。

本地 POSIX 环境可用 `execute` 启动单次任务或顺序计划，执行前按超时上限加终止余量检查预算，结束后自动记录；集群或已有训练器继续使用 `record` 导入真实运行。操作和训练输出约定见 [execution.md](execution.md)。执行前估算 `elapsed_seconds × gpu_count / 3600`，计入失败运行和先前协议的消耗。根据用户已有资源范围执行，不擅自扩预算。并行训练时 GPU 小时是各运行资源占用的总和；共享 GPU 或可变卡数需使用等价资源核算，并在 notes 解释。

每次完成或失败立即 record。已完成运行必须有标量指标 JSON；失败运行有日志、failure_reason 和真实消耗。代码证据应包含完整运行代码或代码包，包含未提交改动，配合 code_revision 和精确命令，不能仅保存一个与训练无关的文件。CLI 验证存在性和哈希，不能鉴定命令是否真的执行或快照是否完整。

正式网格是 `全部 baseline/candidate/ablation × dataset × seeds`。每个单元允许一个 completed confirmatory 记录；失败后可重试，失败记录仍保留。试不同超参的多次运行属于 pilot，不能用重复正式记录挑最好的一次。

若研究不适合全笛卡尔网格（多阶段设计、不同适用域、仅理论工作），应调整框架后再使用机器检查，不要编造空实验填网格。默认三种子是起点，所需重复次数取决于方差、资源与问题；n=1 不报告标准差，不声称统计稳定性。

## 分析与反证

`summarize` 只汇总当前协议下 completed confirmatory 的主指标，按模型和数据集分组，不跨数据集池化。sample_std 是样本标准差；工具不输出 p 值、置信区间或“显著提升”。多次重复的统计单位与独立性需要解释，配对比较和多重比较要采用适合任务的分析。

reports/analysis.md 至少讨论：

- 原预测是否成立；反例、负结果和失败条件。
- 改善是否也可由容量、训练预算或评测差异解释。
- 消融是否真的检验机制；主指标变化与诊断指标是否一致。
- 效果大小、变异来源、成本与适用范围。
- 未完成或超预算单元及其对结论的影响；不能删去失败记录。

审查 experiments 的时候同时阅读 summary、analysis、原始记录和协议。若主张不成立，可以完成有价值的失败分析，也可以停止；不强迫 Agent “找到赢的结果”。

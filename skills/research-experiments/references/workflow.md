# 从材料到可验证的研究问题

本文件只用于研究设计。写作技能不参与问题选择、证据评价和实验决策。

## scope：先约束问题

填 project.json：研究对象、实际失效、拟贡献的知识、数据条件、时间限制和总资源。贡献可来自方法、评测、分析、负结果或应用适配；当前 CLI 主要支持具有模型对比实验的研究。

把“研究长序列预测”收窄为“在相同可用历史和训练预算下，什么条件会让一个已有基线发生可重复的失效？”不能预先填写“提出模块，达到 SOTA”。

检查已有代码、数据许可、可用机器和用户已给出的授权。具体数据或预算未知时，先完成不依赖它的检索与代码检查。对缺少的必要信息集中提问。将假设和未核实事实分开记录。

## literature：建立问题—方法—证据表

先用问题、失败现象、任务别称和机制关键词检索，再沿最接近工作的引用及被引关系交叉检索。为避免只看到支持材料，另检索反例、失败复现和批评。

按 `direct / transfer / context` 分类。第一轮可以读摘要筛选；支撑具体机制、创新判断和实验设计的关键文章需要读正文及相关附录。精确记录引用位置。检索日期、查询式和来源保存在 searches；没搜到不等于不存在。

每篇重点提取：

| 字段 | 要写的内容 |
| --- | --- |
| problem | 观察到了什么失效，发生在什么条件下 |
| mechanism | 作者认为原因是什么，改变了哪段信息流 |
| evidence | 哪个表、图、消融或推导支持解释；只有相关性也要说明 |
| limitations | 哪些条件未测，哪些假设不成立时会失效 |
| relevance | 当前问题是否满足方法依赖的前提 |

synthesis 要综合分歧和缺口，不重复拼接摘要。最低一篇直接相关全文只是工具的结构下限；检索是否充分，由问题范围和近邻覆盖决定。`source_checked=true` 只在真实打开并核对来源后填写，工具不会访问网址替你证明。

## hypothesis：将想法压成一个可证伪判断

填写 hypothesis.json：

1. **baseline_failure**：从真实观察或可核查文献定义失效，给出条件和证据位置。
2. **explanation**：提出一个具体原因，说明它与症状的联系。
3. **intervention**：只改动检验该原因所需的环节。
4. **predictions**：除主指标外，机制成立时应出现什么可观察变化。
5. **falsification**：哪些结果会使你放弃或修改解释。
6. **alternatives**：容量、训练更久、数据泄漏、随机性或实现细节是否也能解释结果。
7. **novelty**：与最接近工作逐项对照，交代复用、改动和新增认识。
8. **evidence_cost**：完整讲清主张需要哪些消融、数据、规模和预算；超出预算则收窄问题。

不要求从零发明模块。组合已有方法可以是贡献，但需要说明为何组合、何时有效、已有工作是否覆盖，及证据增加了什么认识。不能隐藏组合和替换事实。

## 决策与角色

默认由同一个 Agent 顺序切换：研究员负责问题与假设，实验工程师负责实现，审查者专门找反例，作者负责证据表达。角色切换不等于独立复核。有条件且获得授权后可以使用不同模型或人类复查，记录真实身份和所见材料。

每个阶段默认最多三轮审查，优先处理 blocker 和 major。保留描述、证据、关闭方式与复测文件。三轮后仍影响核心结论，或预算已不足时：缩小问题、重新设计研究或明确停止。不要承诺“修到没有任何问题”。详细的候选提案和实验决策见 [innovation.md](innovation.md)。

每次转向在 DECISIONS.md 写清：新证据、原判断、替代方案、选择及成本。已有测试集结果影响了新假设时，要标为探索，不能把同一数据再次包装成独立确认。

# 优化器方向接入示例：以 Muon 为讨论起点

这是待验证的研究计划示例，未运行实验、未主张新颖性、未给出成绩。Muon 只是具体入口；框架也能研究其他优化器或模型。

## 先读已有工作，避免把已有设计当创新

Muon 的原始技术说明区分隐藏层矩阵参数与其他参数的处理，并分别展示按训练量与墙钟比较的结果。开展新研究时，核对实际所用版本的参数分组和训练代码；“对不同参数使用不同优化器”本身不能直接算新点子。来源：[Keller Jordan 的 Muon 技术说明](https://kellerjordan.github.io/posts/muon/)（2024-12-08 的设计说明，不代表当前完整相关工作）。

可从一个**尚待核查的问题**开始：“在相同模型、数据与合理调参预算下，某种更新近似的精度变化，是否影响特定参数组的学习行为；若有影响，收益能否被重新调学习率解释？”这个问句不预设影响存在，也不预设未有人做过。

## 把讨论变为实验

1. 查目标优化器、更新近似、参数分组及竞争解释的近邻论文与官方实现；必要时缩小或更换问题。用 research-ideation 记录支持与反对理由。
2. 接入一套可信的训练代码。固定数据顺序、初始化、参数分组、精度与评测；分别列等训练量和等墙钟比较，因为两者回答不同问题。
3. 先复现基线。检查参数是否更新、更新是否有限、checkpoint 恢复、指标与破坏对照，说明当前小预算可以观察的现象。
4. 若确有相关失效，再登记一个最小干预。比较原版、干预版和重新调学习率的控制，记录损失曲线、相关参数组的更新诊断及实际成本。
5. 运行前写出两个解释的不同预测；结果出来后决定是实现问题、基线欠调、现象不存在，还是值得扩大。诊断结果不能自动外推到大模型。
6. 在可负担的更长训练／代表性尺度检查后，固定方法与配置，做独立确认、多种子和机制消融。若没有支持，保留负结果或转向；不要为了套“Muon 改进论文”而改口径。

## 开始方式

在框架根目录：

```bash
python3 scripts/research.py init --project projects/optimizer-study --topic "优化器机制与效率研究"
```

然后把新目录交给 Agent，提供已有训练仓库／数据位置、可用机器和资源预算。使用 README 的启动提示词或 prompts/ideate.md。没有这些输入时先检索和检查实现，不会凭空产生训练成绩。
